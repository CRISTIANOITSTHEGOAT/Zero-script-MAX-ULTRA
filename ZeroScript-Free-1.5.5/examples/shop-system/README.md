# Modern Shop GUI with Tabs & Currency

A complete, `--!strict`, production-shaped Roblox shop system written to the
"Principal Roblox Systems Architect" brief, and built the way the ZeroScript Dev
Kit wants a system built: **inspect → lint → one atomic write → verify → focus →
play-test → keep the undo points.**

Three files, 1,258 lines, 44,010 bytes, **zero lint findings**.

| Studio path | Class | File | Size | Owns |
|---|---|---|---|---|
| `ReplicatedStorage.ShopConfig` | ModuleScript | `ShopConfig.lua` | 6,557 B | Pure data + `export type`s. No services, no state, no side effects. Safe to `require` from both sides. |
| `ServerScriptService.ShopServer` | Script | `ShopServer.lua` | 15,154 B | Remotes, currency, DataStore, validation, anti-exploit, what owning an item *does*. |
| `StarterGui.ShopClient` | LocalScript | `ShopClient.lua` | 22,299 B | Rendering, TweenService, input. Never decides anything. |

`ShopServer` creates `ReplicatedStorage.ShopRemotes` itself (4 `RemoteEvent`s +
1 `RemoteFunction`), so dropping the three scripts into an empty baseplate is the
whole installation — nothing to build by hand in the Explorer.

## Run it in Roblox Studio (the real pipeline)

With the ZeroScript bridge connected and Studio open, these are the exact calls,
in the order the brief asks for:

```jsonc
// 1. INSPECT — one call replaces a five-turn warm-up
{"tool": "project_overview", "args": {"root": "game", "depth": 3, "scripts": true}}

// 2. PRE-FLIGHT LINT — resolve every finding before writing anything
{"tool": "luau_check", "args": {"files": [
  {"path": "ShopConfig.lua", "code": "..."},
  {"path": "ShopServer.lua", "code": "..."},
  {"path": "ShopClient.lua", "code": "..."}], "context": "script"}}

// 3. ATOMIC WRITE — all three in ONE turn, or none of them
{"tool": "script_write", "args": {"files": [
  {"path": "game.ReplicatedStorage.ShopConfig",   "className": "ModuleScript", "code": "..."},
  {"path": "game.ServerScriptService.ShopServer", "className": "Script",       "code": "..."},
  {"path": "game.StarterGui.ShopClient",          "className": "LocalScript",  "code": "..."}],
  "check": true, "history": true, "select": true}}

// 4. VERIFY — compiles them inside Studio, reports syntax errors with line numbers
{"tool": "script_verify", "args": {"paths": [
  "game.ReplicatedStorage.ShopConfig",
  "game.ServerScriptService.ShopServer",
  "game.StarterGui.ShopClient"]}}

// 5. FIND CODE — mirror once, then grep locally with no Studio round-trip
{"tool": "workspace", "args": {"action": "pull"}}
{"tool": "workspace", "args": {"action": "grep", "pattern": "RemoteEvent", "context": 1}}

// 6. FOCUS — put the human's eyes on what was just written
{"tool": "studio_view", "args": {"select": ["game.StarterGui.ShopClient"],
                                 "focus": "game.StarterGui.ShopClient"}}

// 7. TEST — press B to open the shop, then read Output
{"tool": "playtest", "args": {"seconds": 6, "stop": true, "capture": "both",
  "keys": [{"action": "keyPress", "key_code": "B"}, {"action": "wait", "wait_time_ms": 500}]}}

// 8. UNDO surface — what is on record if any of that was wrong
{"tool": "script_history", "args": {"action": "list"}}
```

`script_write` re-runs the linter itself and refuses the **whole batch** on a
single finding, so step 2 is not decorative: it is the difference between "3
written" and "ERROR: script_write wrote NOTHING". Step 4 is the one the original
brief omits — writing without verifying means discovering a syntax error in the
Output window three steps later.

> DataStore note: Studio needs **Game Settings → Security → Enable Studio Access
> to API Services** on, or `ShopServer` falls back to an in-memory profile and
> says so in Output. That fallback is deliberate: the shop must still be testable
> in a fresh, unpublished place.

## The security model

The client is treated as hostile. Every purchase goes through `onPurchase`, in
this order, and every step can refuse:

1. **Shape.** `typeof(rawItemId) ~= "string"` → refused and flagged. Then
   `ShopConfig.getItem(itemId)` → an id that is not in the config does not exist,
   whatever the client thinks it is worth.
2. **Rate limit.** A rolling 5 s window, max 8 attempts, plus a 0.4 s cooldown
   between purchases — both checked *before* any work is done.
3. **Quantity.** `normaliseQuantity` rejects non-numbers, `NaN` and `±inf`, then
   `math.clamp(math.floor(n), 1, maxPurchaseQuantity)`. A client asking for
   `-50` or `1e308` gets `1` or `10`.
4. **Ownership caps.** `maxOwned` is enforced against the server's own inventory
   record, so a "one per player" item cannot be bought twice by racing two
   requests.
5. **Price.** `math.floor(item.price * quantity)` is recomputed on the server
   from the config. The client never sends a price, and the client's copy of the
   config is never trusted.
6. **Commit, then persist.** Cash is deducted and inventory incremented in one
   place, `leaderstats` is updated from the same numbers, and the save goes out
   through `UpdateAsync` (so two servers cannot race) inside `withRetry` (3
   attempts, backoff).

Refusals are counted per session and `warn`ed with a reason
(`[ShopServer] refused <player> (rate limit) - 3 refusals so far`), which is the
part you actually read while hunting an exploiter. `PlayerRemoving` saves, and
`game:BindToClose` saves again with a Studio-only `task.wait(0.5)` so the last
purchase survives someone pressing Stop.

On the client, `requestPurchase` keeps one purchase in flight (`busy`) with an
8 s watchdog that frees the button if the reply is lost — and a token check, so a
late watchdog cannot unlock a *newer* request that is still waiting.

## The UI contract

Everything the brief specified, and the three places where a literal reading of
it would have been worse:

- **Sizes are Scale only.** Every `Size` in the client is `UDim2.new(sx, 0, sy, 0)`
  — the grid is `CellSize = UDim2.new(0.315, 0, 0.30, 0)`, three across at any
  resolution. Two things are deliberately *not* Scale, and both are positions
  rather than sizes: the toggle is pinned to the bottom-right corner with
  `Position = UDim2.new(1, -16, 1, -16)` and the cash label sits 44 px clear of
  the close button. A corner pin is `Scale 1` plus a pixel margin; that margin is
  not a size and must not scale.
- **Clamped where a tap target matters.** Scale alone would make the close button
  13 px tall in a small window, so the three frames that must stay usable — the
  root (max 1040×700, min 320×240), the toggle (44–72 px) and the close button
  (24–34 px) — are sized in Scale and clamped in pixels by a `UISizeConstraint`.
  The one genuinely pixel-sized `UDim2` in the system is the nameplate's
  `BillboardGui` in `ShopServer`: that is world space, where Scale would mean "a
  fraction of the screen" and stretch the nameplate with the camera.
- **Bounds.** The root also carries a `UIAspectRatioConstraint` (1.55,
  `FitWithinMaxSize`), so it is neither a letterbox on an ultrawide monitor nor a
  tall strip on a phone.
- **Palette** exactly as specified: background `(20,22,28)`, cards `(28,31,39)`,
  borders `(45,50,62)`, accent `(0,190,125)` with `(0,140,255)` as the dim
  accent, text `(245,245,250)`, subtitles `(160,165,180)` — plus `(235,87,87)`
  for refusals and a rarity ramp (common → legendary).
- **Corner / stroke / padding.** `UICorner` `UDim.new(0, 8..12)`, `UIStroke`
  `Transparency 0.7` on containers and cards, `UIPadding` 10–12 px, via three
  tiny builders (`corner`, `stroke`, `padding`) so no card is missing one.
- **Hover.** Buttons tween to **1.05×** with `Enum.EasingStyle.Quad` on
  `MouseEnter`/`SelectionEnter` and back on leave. The tween target is a
  **`UIScale`**, not `Size`: the cards live in a `UIGridLayout`, and tweening
  `Size` fights the layout, which wins. This is the one deviation from a literal
  reading of the brief, and it is the difference between a smooth hover and a
  card that snaps back mid-tween.
- **Recycling.** Cards are tagged `ShopCard` through `CollectionService` and
  cleaned up via `GetInstanceAddedSignal`/`GetTagged`, so re-rendering a tab
  never leaks instances into the scrolling frame.
- **Input.** `Enum.KeyCode.B` toggles, `Escape` closes, shift-click buys a stack
  of 5 for anything stackable, and `processed` is respected so typing in a
  `TextBox` never opens the shop.

## Luau standards

- `--!strict` on all three files; every exported shape has an `export type`
  (`ItemData`, `TabData`, `Palette`, `SoundSet`, `ShopData`) and the config table
  is annotated with it, so a typo in an item id or a missing field is a
  type error at author time.
- `task.wait` / `task.spawn` / `task.delay` only — no `wait`, `spawn`, `delay`,
  no `Instance.new("Part", parent)`. Every builder sets properties first and
  `Parent` last.
- Generalized iteration (`for k, v in t do`) throughout; no `pairs`/`ipairs`.
- `unknown` at every remote boundary, narrowed with `typeof` before use, then
  `::` casts — the client coerces the server's `RequestData` reply the same way
  the server coerces a DataStore profile, because both are untrusted input.
- `local table_` where a variable would otherwise shadow the `table` library.
- `requestPurchase` / `quantityFor` are forward-declared as function *types*
  because rendering a card wires its buy button, and a finished purchase
  re-renders the cards — one of the two has to be declared before it exists.
- Sounds default to `""`, which means silent: nothing fires a made-up asset id at
  the client. Put real ids in `ShopConfig.sounds` and they play.

## What this example cost the linter (and why that is the point)

Writing 1,258 lines of modern Luau through the Dev Kit's own gate found four real
bugs in the tooling. All are fixed, all have regression tests, and none of them
were found by the tests that existed:

1. **`if` used as a value** — `local b = if x then 1 else 2` is closed by its
   `else` and has no `end`. The block scanner read it as an unclosed statement
   `if`, so `script_write` refused perfectly good code. (`3127a8c`)
2. **A literal `else`-branch** — `_mask()` blanks a string literal to spaces, so
   the "is the next thing an `if`?" lookahead after `else` looked *through*
   `else "done"` and found the `if` of a statement two lines later. The stack
   desynced and the error surfaced 200 lines away as a bogus
   `extra 'end' - nothing is open here` on `ShopClient.lua:545`. `_next_significant()`
   now stops *at* a literal instead of skipping it. (`9b0e24a`)
3. **Bytes vs characters** — Luau's `#source` counts bytes, Python's `len()`
   counts code points. These scripts contain `🛒` and `·`, so `script_write` said
   6,557 and `workspace pull` said 6,156 for the same file, and
   `workspace status --compare-live` reported all three freshly written scripts as
   `CHANGED` on a mirror pulled 0 s ago. Every size is now bytes, and says so.
   (`b0c428b`)
4. **`workspace grep`** — overlapping context windows printed shared lines once
   per neighbouring match (15 lines for 5 adjacent hits), and a plain-text search
   lowered the line but not always the needle, so `"regex": false` +
   `"ignore_case": false` could never match `GetService`. (`b0c428b`)

If you change the linter, re-run this example through it:

```bash
cd ZeroScript-Free-1.5.5
python3 -c "
import local_tools as L, os
files = [{'path': n, 'code': open('examples/shop-system/' + n, encoding='utf-8').read()}
         for n in ('ShopConfig.lua', 'ShopServer.lua', 'ShopClient.lua')]
print(L.run('luau_check', {'files': files, 'context': 'script'}, None)['text'])"
```

Expected: `luau_check: clean - 3 snippet(s), 1258 lines, no errors or warnings.`

## The example is in the test suite, so it cannot rot

`tests/test_examples.py` (15 cases) lints all three files on every run — which is
how the next linter change gets checked against 1,258 lines of real modern Luau
instead of only against hand-written snippets — and asserts the standards this
README claims: `--!strict` first, no deprecated scheduler calls, nothing parented
inside `Instance.new`, generalized iteration only, every GUI `Size` in Scale, the
single pixel size living in world space, the exact palette, hover tweening a
`UIScale` and never a `Size`, the config being pure data, the server owning every
decision (and the client never touching `DataStoreService`), and this README
documenting `script_verify` before `playtest`.

Each of those assertions was mutation-checked: break the rule in a throwaway copy
(pixel size, dropped `--!strict`, `pairs()` returning, a bare `wait()`, the client
reaching for the DataStore, `Instance.new("Folder", parent)`, a syntax error) and
the intended test fails. Seven mutations, seven caught, none missed — a test that
cannot fail is worse than no test.
